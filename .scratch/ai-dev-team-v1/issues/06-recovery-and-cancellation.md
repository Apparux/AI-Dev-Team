# 06: 中断后安全接续与取消确认

Milestone: M2 — 持久化与恢复
Status: ready-for-agent

**What to build:** 主管或执行环境中断后，用户可依据持久记录与现场安全接续；取消时能知道哪些执行真正停止、哪些仍待确认，而不会重复修改代码、误抢主管归属或丢失在途成果。

**Blocked by:** 05 — 暂停、动作审批与规则变更确认。

**Execution gate:** 必须已通过 M1 人工关口，且本票包含在用户明确授权的后续批次中；前置验收通过本身不构成执行许可。

## 上下文与范围

对应 [TASKS T05 后半与 M2 出口](../../../TASKS.md)，收口 [PRD A06、A07](../../../PRD.md)；恢复表与取消语义以 [DESIGN 第 5 节](../../../DESIGN.md) 为准。

原生 resume、事件通知和结果文件都不能单独证明业务状态；需要结合执行身份、代码版本、规则、审批与实际会话对账。本票不承诺 exactly-once 或自动唤醒主管。

## Acceptance criteria

- [ ] 主管退出后重新进入，会先确认唯一主管归属，再读取任务、事件、审批、实际会话、成果及规则；旧主管是否仍活跃不明时不自动抢占。
- [ ] 已落盘结果先重新验收；进程消失且已有改动时保留现场并明确接续策略，绝不把“无结果文件”视为“从未执行”。
- [ ] 投递超时/不明时不盲目重发；新 Attempt 或换 Harness 前确认单写入者和代码/成果状态。
- [ ] 取消请求先停止新派发，尝试停止执行并记录未停止项；停止未确认时不进入彻底 cancelled，不自动删除工作区或回滚代码。
- [ ] 迟到、旧 Attempt、旧规则下或取消中的结果保留对账价值，但不能覆盖当前结果或将 Run 自动推进为 completed。
- [ ] 分别以最小场景演练主管退出、投递不明、客户端 detach 和隔离 server 重启；清楚区分原生会话恢复与业务恢复，并保留实际证据。

## 验证与执行约束

server 中断仅在用户明确授权的独立测试环境演练，不重启共享服务。Ctrl+C 后检查真实状态，不假定发送按键就等于停止。测试未具备安全前提时标为阻塞/未验证，而不是更改权限或扩大环境操作范围。
